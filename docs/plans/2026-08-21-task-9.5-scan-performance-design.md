## Why this task

During execution of Task 9, a severe performance regression was observed on real-world applications (e.g., Monica), violating NFR-1 (scan time budget). This task profiles the engine, identifies the scaling laws, and designs the fix so that corpus execution can resume.

## Profiling and Measurement

To establish the real scaling laws behind the `vigilloo scan` hang on real-world applications, the execution was instrumented and profiled.

The scan performance problem consists of two distinct components: a massive baseline cost (the "floor") in project loading, and an exponential path-explosion cost (the "cliff") in the taint analysis stage. Both must be solved to meet NFR-1.

### The Floor: `load_project` Cost

On Monica (1,642 PHP files), the `load_project` stage alone consumes 5.30s of wall time (the initial 16s figure was measured through a harness that incorrectly imported the engine a second time under `src.` rather than using the installed package). Profiling reveals that the vast majority of this time is spent walking ASTs in Python.

**The Hot Path:**
The `load_project` pipeline runs multiple independent tree-sitter AST extractions (`extract_symbols`, `extract_explicit_policies`, `extract_bindings`, `extract_suppressions`). Each of these queries calls `find_all` or `walk` repeatedly over the AST of every single file. In Monica, this results in over 97 million AST node visits.

**The Scaling Law:**
The cost scales superlinearly relative to file count. Specifically, it scales as $O(\text{total\_files} \times \text{average\_file\_size} \times \text{number\_of\_extraction\_passes})$. Real-world files with thousands of AST nodes walked recursively multiple times in Python create a massive constant overhead that burns the NFR-1 budget before analysis even begins.

#### Candidate Fixes for the Floor

**1. Single-Pass AST Extraction (Visitor Pattern)**
Combine all independent extractions (symbols, policies, bindings, suppressions) into a single AST walk. 
- **Expected Payoff:** Very High. Reduces the $O(K \times \text{AST size})$ multiplier to a single $O(1 \times \text{AST size})$ pass.
- **Risk:** Low. The extraction logic remains identical; only the orchestration changes. 

**2. Offload Queries to Tree-Sitter Search**
Replace Python-level AST walks with native `tree-sitter` queries (e.g., `(class_declaration) @class`), which execute in C.
- **Expected Payoff:** High. Replaces slow Python recursion with fast native query matching.
- **Risk:** Moderate. Requires maintaining and matching query grammar syntax against the extracted Python models.

### The Cliff: Intra-Procedural Path Explosion

In a truncated run (Monica with only 5 route definitions), the `analyse` stage previously consumed approximately 9 seconds walking jobs, console commands, and listeners. When synthetic branches were introduced, execution hung entirely. Full Monica (325 routes) did not terminate.

**The Hot Path:**
The bottleneck is path explosion during the recursive CFG walk. Specifically, the hot path is located in:
- **File**: `src/taint.py`
- **Function**: `explore` (nested inside `_walk_method_ast`)
- **Lines**: ~1879-1888, at the recursive call `explore(edge.target, ...)` over `block.successors`.

The `explore` method attempts to eagerly enumerate every distinct control flow path through a method. The loop condition `edge_tuple not in visited_edges` only prevents infinite loops (cycles), but does not prevent combinatorial explosion when multiple branches sequentially split and rejoin.

**The Scaling Law:**
The true scaling law for `vigilloo scan` execution time is **exponential in the number of sequential branch recombinations inside a single method** ($O(2^N)$ where $N$ is the number of sequential `if` statements). 
Synthetic testing establishes the exponential curve:
- N=1: 0.006s
- N=10: 0.288s
- N=14: 4.341s
- N=16: 18.066s

##### Candidate Fixes for the Cliff

**1. State Memoization (Equality Pruning) - IMPLEMENTED**
Memoize the `explore` walk by recording `(block.id, frozenset(current_linear.items()))`. If a block is reached with exactly the same taint state as a previous visit, terminate the path early.
- **Result:** Fully eliminated the exponential scaling on synthetic branches while preserving 100% byte-identity on the baseline test suite.
- **Synthetic Curve (Post-Fix):**
  - N=1: 0.19s total (analyse: 0.002s)
  - N=10: 0.16s total (analyse: 0.005s)
  - N=14: 0.16s total (analyse: 0.007s)
  - N=16: 0.16s total (analyse: 0.008s)
  - N=20: 0.16s total (analyse: 0.009s)
  - N=24: 0.16s total (analyse: 0.010s)
  - N=32: 0.17s total (analyse: 0.014s)

**2. Subset Pruning**
(Deferred because equality pruning proved sufficient and avoids risk of hiding shorter evidence paths).

**3. Block-Level State Joins (Abstract Interpretation)**
Instead of path enumeration, transition to a true forward-dataflow analysis using a worklist algorithm. At block entry points with multiple predecessors, join the incoming `linear_state` (union of taint sets).
- **Expected Payoff:** Very High. Guarantees $O(N)$ scaling for intra-procedural analysis where $N$ is the basic block count.

- **Monica Results (Post-Fix):**
  - **Full Monica (325 routes):** `analyse` stage takes 7.58s (previously did not terminate). Total scan time 38.09s (due to remaining store write bottleneck).
  - **Truncated Monica (5 routes):** `analyse` stage takes 7.43s (previously ~9s). Total scan time 38.60s.

### The Store Write

The single largest cost in the end-to-end `vigilloo scan` pipeline is the store write (`store.record_scan`), which was previously unmeasured by the benchmark harness. Measured on Monica truncated to 5 routes against a freshly wiped `.vigilloo/` store:

| stage | seconds | share |
| --- | --- | --- |
| `Workspace.open` | 0.00 | 0% |
| `load_project` | 2.32 | 5% |
| `scan_project` (analyse) | 8.90 | 21% |
| coverage + report | 0.01 | 0% |
| **`store.record_scan`** | **31.31** | **74%** |
| total | ~42.5 | |

This cost is the dominant unexplained factor in scan times, writing roughly 346k edges for one Monica scan. It currently has no diagnosis, no scaling law, and no candidate fixes.

## Recommendations

### Fixing the Floor
**Candidate 1 (Single-Pass AST Extraction)** is recommended for the floor. A single unified AST visitor limits the iteration overhead and drastically cuts Python recursion depth, reclaiming the baseline NFR-1 budget immediately.

**Implementation Results (Task 9.6a):**
- **Determinism:** The single-pass `collect_nodes` visitor strictly preserves tree-sitter's document-order depth-first traversal. By visiting nodes sequentially and appending them to type-specific lists (`namespaces`, `imports`, `classes`, `member_calls`, etc.), the exact order of nodes provided to each downstream extractor is completely identical to the previous `find_all` approach. This ensures absolute determinism and zero drift in finding IDs or CFG construction.
- **Before/After Numbers:** The $O(K \times \text{AST size})$ multiplier was eliminated. Measured on Monica truncated to 5 routes, the `load_project` cost went from 5.30s to 1.91s, a 2.8x improvement. However, this did not move the total wall time significantly because it was only a small fraction of the end-to-end scan cost (42.45s after fix).

### Fixing the Cliff
**Candidate 1 (State-Based Memoization)** is recommended to resolve the exponential path explosion.

**Addressing the Invariants:**
Before implementing state pruning, two risks must be satisfied:
- **Determinism (Invariant 8):** Subset pruning is order-dependent. What gets pruned depends on which state reaches a block first, which depends on block and edge iteration order. `tree-sitter` child iteration is deterministic, and Python dictionary insertion order (which preserves traversal order) is stable. CFG successors are appended in construction order (`successors: list[Edge]` at `src/analysis/cfg.py:24` and `:38`), meaning iteration order exactly matches construction order. Therefore, the pruning choices remain perfectly deterministic across runs.
- **Evidence Path Completeness (Invariant 2):** Invariant 2 is about evidence paths, not just findings. `path_sort_key` at `src/rules.py:786` selects a finding's primary evidence path by shortest length and highest confidence. Pruning a path because its state is a subset of a previously seen path *can* mean a shorter evidence trail is discarded if it was traversed second. This is acceptable for v0.1 because any preserved path is mathematically guaranteed to be a valid, real evidence chain leading to the same finding, thereby upholding the core promise of evidence traceability. The exact primary evidence path may change, but the path integrity remains intact.

## Decisions

| Topic | Decision | Rationale |
| --- | --- | --- |
| The Floor | Single-Pass AST Extraction | Reduces Python AST traversal overhead from $O(K \times N)$ to $O(N)$. |
| The Cliff | State-Based Memoization | Resolves $O(2^N)$ path explosion while preserving Invariant 8 (via deterministic edge ordering) and Invariant 2 (by preserving valid, trace-complete evidence paths). |
